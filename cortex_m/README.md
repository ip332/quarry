# Cortex-M cross-compilation validation

This directory cross-compiles Quarry's generated C code
(`compiler/backend_c/`) and strict-C99 C runtime (`Quarry::runtime_c`) for a
generic ARM Cortex-M4 target using the GNU Arm Embedded toolchain
(`arm-none-eabi-gcc`), and reports the resulting flash/RAM footprint.

**Scope.** This proves Quarry's generated C code and runtime *build and
link* for a resource-constrained bare-metal target. It does not run
anything on real or emulated hardware, and it is not a board support
package: there is no HAL, no RTOS, no flashing support, and the linker
script/startup file exist only to produce a linkable ELF for footprint
measurement, not to boot real silicon. The Cortex-M4/soft-float
architecture flags and the illustrative STM32F446-class memory map are a
representative profile, not a certification that Quarry runs on that or
any other physical part. See `docs/roadmap.md`'s "Cortex-M validation"
entry for what is and isn't covered, and what remains future work
(physical hardware/QEMU execution, footprint regression gating, additional
Cortex-M profiles, RTOS/Zephyr integration).

## Why this is a separate CMake project

This is **not** `add_subdirectory()`'d from the repository's root
`CMakeLists.txt`. The root project builds host tooling (the schema
compiler, its protobuf/absl/libyaml dependencies, gtest-based tests) that
has no business being cross-compiled for a bare-metal target, and
`CMakePresets.json` presets are bound to the CMakeLists.txt in the same
directory, so there is no way to express "cross-compile just this part" as
a preset on the root project. `cortex_m/` is therefore its own standalone,
opt-in CMake project, analogous in spirit to `fuzz/`: a development/
validation tool, not part of the installed SDK (`Quarry::runtime`,
`Quarry::runtime_c`, `Quarry::schema_compiler` remain the only public
surface -- see `docs/distribution-model.md`).

## The two-stage flow

Cross-compiling Quarry's C output requires three distinct artifacts,
supplied explicitly (this project does not build or auto-discover any of
them itself, matching the policy in
`docs/schema-compiler-tool-distribution.md`'s "Host Tool and
Cross-Compilation Policy"):

1. A **host-built** `quarry-schema-compiler` (native, runs on the build
   machine) -- used to generate C source from the representative schemas.
2. The **target runtime** headers (`include/quarry/runtime_c/`, plus the
   version header generated by configuring the root project).
3. The **generated C code** itself, produced by (1) and compiled by the
   Cortex-M cross-compiler alongside the runtime and a small smoke test.

```sh
# 1. Build a host quarry-schema-compiler (from the repository root).
cmake --preset debug   # or docker-debug inside the dev container
cmake --build --preset debug --target quarry_schema_compiler

# 2. Configure and build the Cortex-M cross build.
cmake -S cortex_m -B cortex_m/build \
  -DCMAKE_TOOLCHAIN_FILE=$(pwd)/cmake/toolchains/arm-cortex-m4.cmake \
  -DQUARRY_HOST_SCHEMA_COMPILER=$(pwd)/build/debug/tools/quarry-schema-compiler \
  -DQUARRY_RUNTIME_C_INCLUDE_DIR=$(pwd)/include \
  -DQUARRY_RUNTIME_C_VERSION_HEADER_DIR=$(pwd)/build/debug/generated
cmake --build cortex_m/build

# 3. Report footprint.
python3 cortex_m/scripts/report_footprint.py \
  --elf cortex_m/build/quarry_cortex_m_smoke.elf \
  --object generated_workload=cortex_m/build/CMakeFiles/quarry_cortex_m_smoke.dir/generated/benchmark/workload.generated.c.obj \
  --object generated_shared=cortex_m/build/CMakeFiles/quarry_cortex_m_smoke.dir/generated/benchmark/workload/shared.generated.c.obj \
  --object smoke=cortex_m/build/CMakeFiles/quarry_cortex_m_smoke.dir/smoke/workload_smoke.c.obj \
  --object startup=cortex_m/build/CMakeFiles/quarry_cortex_m_smoke.dir/startup_cortex_m4.c.obj
```

This is exactly what CI runs (`.github/workflows/ci.yml`, "Cortex-M Cross
Build" job).

## What gets cross-compiled

The smoke target (`quarry_cortex_m_smoke`) links:

- `startup_cortex_m4.c` -- a minimal Cortex-M4 vector table and
  `Reset_Handler` (plain C; ARMv7-M loads the initial stack pointer and
  program counter from the vector table in hardware, so no hand-written
  assembly reset preamble is required).
- The C code generated from `benchmarks/schemas/workload.brd` and
  `workload_shared.brd` -- reused by reference (not duplicated) from the
  existing native benchmark harness. Together these schemas exercise
  scalar fields, a local enum, a bounded string, bounded bytes, a bounded
  scalar array, a cross-namespace nested record, and a cross-namespace
  array of records.
- `smoke/workload_smoke.c` -- statically constructs a populated
  `benchmark_workload_Workload_t` (including its nested and array-of-record
  `Child` fields) and round-trips it through the generated
  `_init`/`_encode`/`_decode` codec backed by `Quarry::runtime_c`. It makes
  no libc I/O calls (no `printf`, no `assert()`) and stores results in
  `volatile` globals so the calls cannot be optimized away.

## Toolchain

`cmake/toolchains/arm-cortex-m4.cmake` targets a generic Cortex-M4 core
(`-mcpu=cortex-m4 -mthumb -mfloat-abi=soft`, no `-mfpu=...`) with no board
coupling. Soft-float is deliberate: Quarry's generated code and runtime
never use floating-point hardware capability, and this keeps the toolchain
file valid for both FPU and non-FPU Cortex-M4 parts. See the toolchain
file's own comments for the full rationale.
