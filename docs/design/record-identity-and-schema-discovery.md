# Record Identity and Schema Discovery

Status: **accepted; Stage A in progress.** A1 (C++ include guards) is merged (#81). A2 (hierarchical
record IDs, §3) is implemented in the layout pass. A3 onward are not implemented.
`v0.1.31-rc.1` is blocked on Stage A.

## 1. Summary

A Quarry **configuration** is one top-level schema plus everything it imports, directly or transitively.
The compiler numbers records hierarchically within that configuration:
`record_id = (domain_id << 16) | local_record_id`. Each namespace is a domain, numbered by sorted
namespace name; records are numbered by sorted name within their namespace. Neither depends on import
order or traversal.

Every backend, QBS, the generic runtime and the inspector use exactly these IDs. Code may be generated
for selected namespaces, but IDs always come from the complete configuration.

The configuration's identity is QBS's existing `schema_id`, reused unchanged. Its input already covers
every record ID, FQN and wire definition.

A Schema Descriptor and a three-level discovery protocol let a cloud service identify each vehicle's
configuration, classify compatibility, and decode or translate data during OTA rollouts.

Stage A, which blocks the release, delivers:

- hierarchical IDs;
- root-wide, selectable generation;
- the C++ include-guard fix;
- the full cross-language matrix;
- deterministic identity, exposed in generated code and through `--describe`;
- specifications.

Stage B delivers the binary descriptor section, discovery messages, partial retrieval, compatibility
negotiation and gateway translation.

## 2. Findings from the current implementation

| Area | Current behavior | Consequence for this design |
|---|---|---|
| Import loading (`frontend/yaml_compiler.cpp`) | Depth-first, each file's `imports:` in declaration order; a canonical path is loaded once; cycles are rejected (`emit_cycle`); units are registered after their imports | Traversal is well defined and acyclic; duplicate imports already collapse |
| Namespaces | Several files may contribute records to one namespace in a compilation; a test compilation of `truck.engine.Rpm` and `truck.engine.Coolant` from two files produced one QBS image listing both | Namespace-as-domain fits existing semantics |
| Generation (`output_planning`) | Only the root unit emits output; dependencies are generated by separate runs | Must change: separate runs would embed different configurations' IDs |
| Multi-file namespaces | Generating two files of one namespace separately writes the same `truck/engine.generated.h`, and **the second overwrites the first** | Pre-existing defect, fixed by root-wide generation |
| Record IDs (`layout/layout.cpp`) | `index + 1` over the FQN-sorted records of the compilation; copied unchanged by Schema IR, QBS and every backend | The new algorithm replaces one function |
| QBS `schema_id` | SHA-256/128 over the BRF contract, every record FQN and `record_id`, field layouts, enums, arrays and nested references; excludes names, comments, source paths, import paths and the compiler version | Reusable as the configuration fingerprint (§5) |
| QBS extension sections | The spec reserves kinds `0x8000–0xFFFF` and lets readers skip unknown sections whose flags mark them ignorable. **The compiler-side parser rejects any unknown kind or nonzero flags**; the C generic runtime ignores unknown kinds | The compiler-side parser must be fixed before any descriptor section ships |
| C generic runtime | Does not expose or verify `schema_id` | Devices cannot report or check identity from QBS today |
| Version metadata | Git builds report a numeric development version (`0.1.269-dirty`); the prerelease tag exists only in release-archive metadata | A release identity field is needed for "version including prerelease" |
| Generic runtime nested records | Located by QBS table index; the child header must equal the referenced record's `record_id` | Works unchanged with hierarchical IDs |

## 3. Record ID assignment (normative proposal)

### 3.1 Definitions

- **Configuration root**: the schema file given to the compiler.
- **Configuration**: the root plus the transitive closure of its imports, including records that nothing
  references.
- **Domain**: a namespace that declares at least one record in the configuration. Its identity is the
  namespace FQN, or `""` for the unnamed root namespace. Namespaces that declare only enums have no domain,
  because enums carry no wire ID.
- **Canonical identity**: the record FQN. **Wire record ID**: the BRF header value.
  **Compilation-local index**: a record's position in the QBS record table. These are three separate
  concepts.

### 3.2 Domain IDs

**Decision: domains are numbered by sorted namespace FQN.**

1. Collect the domains of the configuration: every namespace that declares at least one record anywhere
   in the configuration's import closure.
2. Sort their FQNs by bytewise comparison of the UTF-8 spelling, with the unnamed root namespace `""`
   first if present.
3. Number them 1, 2, … in that order.

Import order, traversal order, duplicate imports and which file of a namespace is reached first have no
effect. Import cycles are rejected before this step, as today. Domain `0x0000` is reserved, application
domains are `0x0001`–`0xFEFF` (at most 65,279; exceeding that is compile error `BC7004`), and
`0xFF00`–`0xFFFF` are 256 Quarry system domains, each given an explicit constant by the BRF
specification when defined (none is defined yet). The ranges are part of the protocol contract; see
"recordId Structure and Reserved Ranges" in `docs/specifications/binary-record-format.md`.

The configuration root's namespace is *not* necessarily domain 1; it's numbered like every other namespace.

### 3.3 Local record IDs

Within a domain, order the record names (the last FQN segment) by bytewise comparison of their UTF-8
spelling and assign 1, 2, …. Declaration order and file order have no effect. Local `0x0000` and
`0xFFFF` are reserved, so application locals are `0x0001`–`0xFFFE`: at most 65,534 records per domain;
exceeding that is compile error `BC7005`. The namespace comes from the schema's canonical namespace
declaration (`SemanticRecord::namespace_fqn`), not from parsing the FQN; the layout pass checks that
FQN = namespace + `.` + name (`BC7006`).

### 3.4 Wire record ID

`record_id = (domain_id << 16) | local_record_id`, written big-endian in the BRF v2 header as today.
Consequences:

- Every valid ID is at least `0x00010001`, and every ID below `0x10000` is invalid. Every RC3-era ID was
  below `0x10000`, so legacy records are detectable and always rejected.
- Nested records carry their own domain's ID; there is no inheritance from the parent.
- IDs are local to the configuration. The same record has different IDs in different configurations, so a
  receiver must know the sender's configuration (§6) before interpreting any ID.

### 3.5 Diagnostics

The compiler reports these as errors: too many domains (`BC7004`), too many records in a domain
(`BC7005`), duplicate record FQNs (`BC7002`, and earlier in semantic validation), a record whose FQN is
not its namespace plus name (`BC7006`), and import cycles. Schema IR validation still rejects zero or
duplicate IDs (impossible by construction).

### 3.6 Remaining churn

Sorted-namespace numbering removes churn from import order and traversal: reordering imports, adding an
import of an existing namespace, or reaching a shared namespace from a different component changes
nothing.

IDs still change in two cases. Both are expected, and `schema_id` changes with them (§5):

- **Adding or removing a domain** shifts the domain IDs of every namespace that sorts after it. For
  example, adding `truck.aftertreatment` (which sorts before `truck.brakes`) shifts `truck.brakes`
  onward by one.
- **Adding or removing a record** shifts the local IDs of records that sort after it within the same
  namespace only.

Explicit domain pinning would remove even this, but it needs persistent state, which was deliberately
ruled out.

## 4. Generation from the configuration root

- The CLI compiles the configuration root. `--generate <ns>[,<ns>...]` selects namespaces (default: all
  domains). IDs, QBS output and `schema_id` never depend on the selection.
- Every backend then emits one file per selected namespace, containing *all* of that namespace's
  records. This fixes the multi-file overwrite.
- Compiling an imported file on its own remains valid but **defines a different configuration**. The
  compiler can't reliably tell whether a file is "the" root, so instead of guessing with a warning:
  1. `--describe` and every generated file record the configuration root's identity and `schema_id`;
  2. generated files check that every generated file they depend on came from the same `schema_id`, at
     compile time in C, C++ and Go and at import time in Python. Mixing code from two configurations
     fails to build.

  **This is build-time consistency, not runtime negotiation.** The check applies only between generated
  files that reference one another within one generation output (a header including a dependency's
  header, a package importing a dependency's package). It never prevents an application from
  deliberately containing several configurations, as a cloud service does during OTA rollouts. Choosing
  which configuration decodes a given message is a runtime decision, based on the sender's `schema_id`
  (§9); it isn't enforced by generated code.

  To make several configurations coexist in one program, generated names must not collide. Go already
  separates configurations by import prefix. A4 adds an opt-in per-configuration name prefix for the
  other languages:

  - C: a symbol prefix (for example `cfgA_truck_engine_EngineStatus_t`);
  - C++: an outer namespace (`cfgA::truck::engine`);
  - Python: a package prefix.

  The prefix changes only names, never IDs or `schema_id`.

  A warning remains possible for generation from a root that has no importers among the given inputs.
  That's an open question (§12).
- The CMake helper takes the configuration root plus `GENERATE <namespaces>`.

## 5. Configuration identity

**Reuse QBS `schema_id` unchanged** (algorithm 1: SHA-256/128 over the canonical identity input).

- It already includes every record's FQN and `record_id`. The domain mapping can be derived from those
  (the high bits of each ID plus the FQN's namespace), so it needs no separate input.
- It includes all wire-relevant definitions and the BRF contract. It excludes names, comments, import
  paths and the compiler version. So a new compiler that produces identical bytes keeps the same
  configuration identity, as required.
- It changes whenever any ID changes, including after an import reorder, which is what OTA
  discrimination needs.

Challenges and limits:

- **It identifies whole configurations only.** A change to any one record gives a new `schema_id`, even
  for vehicles that never use that record. Per-record fingerprints (§7) handle partial compatibility.
- **Partial QBS images** (§8, level 2) would get a different `schema_id`, because the input covers the
  image's records. A subset must therefore carry its parent configuration's `schema_id` separately from
  its own content ID.
- **Device-side availability:** the C runtime doesn't expose or verify `schema_id`. Stage A adds a
  read-only accessor; verifying it on the device needs SHA-256 in the runtime, which is a footprint
  question and belongs to Stage B.
- **128 bits** is sufficient for discrimination and uncoordinated identifiers.

## 6. Schema Descriptor

### 6.1 Contents

| Item | Kind | Source |
|---|---|---|
| Descriptor format version | compatibility | new |
| `schema_id`, `schema_id_algorithm` | compatibility | QBS header |
| BRF format version (2) | compatibility | QBS identity input |
| QBS format version (1) | compatibility | QBS header |
| Required capabilities (bitset; §6.2) | compatibility | new |
| Domain ID → namespace | compatibility (derivable) | new table, string references into the QBS identity strings |
| Record ID → canonical FQN | compatibility | QBS record table and identity strings |
| Record wire fingerprint and shape fingerprint (§7) | compatibility | new |
| Configuration root identity (root file's namespace and record) | informational | new |
| Quarry compiler version (numeric, plus release tag such as `v0.1.31-rc.1`, plus Git SHA) | informational | version metadata (needs a release-tag field) |
| Schema IR version | informational | Schema IR |
| Optional capabilities | informational | new |

**Rule:** only *compatibility* items take part in classification (§7). Informational items never cause
an incompatibility verdict. In particular, different compiler versions don't imply wire incompatibility.

### 6.2 Capabilities

Two 32-bit sets, *required* and *optional*.

- **Required** bits name what a reader must understand to decode the configuration: BRF v2 record
  layout, hierarchical record IDs, inline fixed nested records, variable arrays, record arrays, string
  arrays, enum widths above 8 bits.
- **Optional** bits name extra metadata present: reflective names, partial retrieval supported, wire
  fingerprints present.

A reader that finds an unknown *required* bit must treat the configuration as incompatible. Unknown
*optional* bits are ignored.

### 6.3 Packaging

The descriptor is a QBS extension section, kind `0x8001` ("configuration descriptor"), flagged ignorable.
The QBS format version stays 1, and there's no new binary format. `quarry-brf-inspect --describe` (and
`quarry-schema-compiler --describe`) prints it as canonical text for people and cloud tooling.

Prerequisites:

- Fix the compiler-side QBS parser to honor the ignorable-section rule.
- Test that images with the section still load in the C runtime and inspector, and in RC3-era C
  runtimes, which ignore unknown kinds.

### 6.4 Stage A evaluation: minimal identity-only descriptor

**Recommendation: no binary section in Stage A.** Ship identity through things that already exist or are
very low risk:

1. QBS `schema_id`, unchanged;
2. the `schema_id` embedded in generated code in every language (§4);
3. `--describe` text built from the QBS image plus version metadata, covering levels 0 and 1;
4. a C runtime accessor for `schema_id`.

The binary section and the parser fix move to Stage B with the discovery protocol, where their
format-design choices can be made together. That keeps the RC free of new wire-adjacent format work.

## 7. Fingerprints and compatibility classification

Two fingerprints per record, each SHA-256 truncated to 64 bits over the canonical QBS identity encoding:

- **Wire fingerprint**: the record's own identity-input slice, *including* its `record_id`, plus the wire
  fingerprints of every record it references, transitively. This identifies the exact bytes the record
  produces. A parent depends on its children's definitions, because inline nested records fix the
  parent's slot sizes.
- **Shape fingerprint**: the same, but with every `record_id` (own and nested) removed and references
  expressed by FQN. It identifies the layout regardless of the configuration's numbering.

For a consumer that needs record set *R*, when comparing configuration A (sender) with B (receiver):

| Class | Condition | Meaning |
|---|---|---|
| **Exact match** | `schema_id(A) == schema_id(B)` | same configuration |
| **Wire compatible** (for *R*) | every record in *R* has the same FQN, `record_id` and wire fingerprint in A and B | B's decoders accept A's bytes for *R* unchanged |
| **Translatable** (for *R*) | every record in *R* has the same FQN and shape fingerprint in A and B, but some IDs differ | a gateway can rewrite header IDs, nested headers included, at offsets known from the schema, with no re-encoding |
| **Incompatible** | otherwise, or an unknown required capability | must not be decoded |

Schema evolution beyond identical shapes (for example added fields) is out of scope here. It would extend
"translatable" later.

## 8. Schema discovery (Stage B)

Discovery messages are BRF records defined by a Quarry schema of their own (`quarry.discovery`), so
there's no new format and every runtime can decode them. The protocol doesn't depend on the transport.

| Level | Request | Response |
|---|---|---|
| **0: identity** | (none) | descriptor version, `schema_id` and algorithm, BRF/QBS versions, required and optional capabilities, informational compiler and Schema IR versions |
| **1: mappings** | filter by domain IDs and/or record IDs, cursor, `max_response_bytes` | domain table and record table entries (ID, FQN, wire and shape fingerprints), plus a continuation cursor |
| **2: definitions** | record IDs, `include_dependencies` flag, cursor, `max_response_bytes` | a partial QBS image containing those records and their transitive dependencies, its content ID and the parent `schema_id`, streamed in chunks |

**Bounded memory.** Every list in the discovery schemas has a declared `max_elements`. Responses are
paged by cursor and never exceed the requester's `max_response_bytes`. Level 2 streams chunks of a size
fixed per session. Responders work from the stored QBS image without building per-request state beyond
the cursor.

**Input validation.** Requests are decoded by generated decoders, which bounds every field. Filters
naming unknown IDs return explicit "not found" entries. Received QBS chunks are validated by the QBS
parser after reassembly.

**Integrity.** The receiver recomputes `schema_id` (or the partial image's content ID) and compares it
with the claimed value.

**Authentication and authorization** belong to the transport (for example mutual TLS or the vehicle
security gateway). The discovery messages carry no credentials.

## 9. OTA operation

1. **Release time.** CI compiles each vehicle software configuration and uploads its QBS image, keyed by
   `schema_id`, to a cloud schema registry. The generated cloud decoders are versioned by `schema_id`;
   Go packages use an import prefix per configuration.
2. **Session start.** The vehicle reports its `schema_id`. Legacy firmware with IDs below `0x10000` is
   identified as such.
3. **Selection.** The cloud looks up the registered configuration. If it's unknown, it falls back to
   level 1 and 2 discovery from the vehicle (Stage B).
4. **Rollouts.** During a rollout, vehicles on configurations A and B coexist. For each processing
   pipeline (record set *R*), the cloud computes the A/B class (§7). Wire-compatible configurations share
   decoders; translatable ones go through ID translation; incompatible ones go to per-configuration
   decoders or are rejected.

## 10. Reference architecture: Class 8 truck

Schemas (`imports` in the order listed):

| File | Namespace | Record | Imports |
|---|---|---|---|
| `truck.brd` (root) | `truck` | `VehicleSnapshot` | `engine.brd`, `transmission.brd`, `brakes.brd`, `cms.brd` |
| `engine.brd` | `truck.engine` | `EngineStatus` | `common_time.brd`, `engine_faults.brd` |
| `engine_faults.brd` | `truck.engine` | `FaultCode` | `common_time.brd` |
| `transmission.brd` | `truck.transmission` | `GearState` (nests `truck.engine.EngineStatus`) | `common_time.brd`, `engine.brd` |
| `brakes.brd` | `truck.brakes` | `BrakeStatus` | `common_time.brd`, `abs_event.brd` |
| `abs_event.brd` | `truck.brakes` | `AbsEvent` | `common_time.brd` |
| `cms.brd` | `truck.cms` | `CameraHealth` | `common_time.brd` |
| `common_time.brd` | `truck.common` | `Timestamp` | (none) |

**Domains** (sorted namespace FQNs; note `truck.cms` < `truck.common` because `m` < `o`):

| Domain | Namespace |
|---:|---|
| 1 | `truck` |
| 2 | `truck.brakes` |
| 3 | `truck.cms` |
| 4 | `truck.common` |
| 5 | `truck.engine` |
| 6 | `truck.transmission` |

**Record IDs:**

| Record | Domain | Local (by name) | `record_id` |
|---|---:|---:|---|
| `truck.VehicleSnapshot` | 1 | 1 | `0x00010001` |
| `truck.brakes.AbsEvent` | 2 | 1 | `0x00020001` |
| `truck.brakes.BrakeStatus` | 2 | 2 | `0x00020002` |
| `truck.cms.CameraHealth` | 3 | 1 | `0x00030001` |
| `truck.common.Timestamp` | 4 | 1 | `0x00040001` |
| `truck.engine.EngineStatus` | 5 | 1 | `0x00050001` |
| `truck.engine.FaultCode` | 5 | 2 | `0x00050002` |
| `truck.transmission.GearState` | 6 | 1 | `0x00060001` |

**Nested records.** A `GearState` record contains an `EngineStatus` header carrying `0x00050001` and a
`Timestamp` carrying `0x00040001`. Each keeps its own domain.

**Selective generation.** The engine ECU build runs `--generate truck.engine,truck.common` and gets two
packages with exactly the IDs above and the same `schema_id` as the full configuration.

**Import-order change.** If `truck.brd` lists `brakes.brd` first, nothing changes: the namespaces are the
same, so the domains, record IDs and `schema_id` are identical. Under the earlier import-order proposal,
this edit would have renumbered four domains.

**Adding a domain.** Release C adds namespace `truck.aftertreatment`, which sorts before `truck.brakes`.
It becomes domain 2 and shifts `truck.brakes` through `truck.transmission` by one (`EngineStatus` becomes
`0x00060001`). That gives a new configuration whose shapes are unchanged for existing records, so it's
*translatable* (§7) from A or B, not wire compatible.

**OTA coexistence.** Release B adds `truck.cms.MirrorFold`, which sorts after `CameraHealth` and gets
`0x00030002`. Nothing else changes. Pipelines that consume `EngineStatus` see equal wire fingerprints in A
and B, so they're wire compatible and share decoders, even though the `schema_id` values differ.

**Independently compiled supplier firmware.** The engine supplier compiles `engine.brd` as its own
configuration root. Its domains are `truck.common` = 1 and `truck.engine` = 2, so `EngineStatus` =
`0x00020001`.

- That number equals `truck.brakes.AbsEvent` in the truck configuration. **Interpreting IDs without
  knowing the configuration is unsafe**, which is why the `schema_id` handshake is mandatory.
- Integration options:
  1. **Preferred:** the supplier builds against the OEM's configuration root and `--generate`s only its
     namespaces, giving an exact match.
  2. **Otherwise:** the configurations are translatable for the engine's record set, and a gateway
     rewrites IDs (Stage B).

## 11. Compatibility and format impact

- **BRF:** stays v2, and the header layout is unchanged. Only the ID values change.
- **QBS:** stays v1. Stage A adds nothing. Stage B adds an ignorable extension section and fixes the
  compiler-side parser.
- **Schema IR and generated-code API epochs:** unchanged by the ID rule. Embedding `schema_id` in
  generated code adds a constant and a check. It needs no new runtime symbols (Stage A uses existing
  ones), so no epoch bump is expected; confirm per backend during implementation.
- **RC3 data:** rejected by design (IDs below `0x10000`). This is a documented break.
- **Workflow:** dependencies are no longer generated by separate runs. The CMake helper, examples, the
  Python and Go cross-namespace instructions, and `tools/README.md` change.
- **Superseded proposals:** the record-ID dictionary and manifest direction is dropped
  (`docs/specifications/manifest-format.md` should be marked superseded). The FQN-hash exploration
  stays on the unpushed local branch `explore/fqn-hash-record-ids`.

## 14. Risks

1. **Domain churn from adding or removing namespaces** (§3.6) leads to new configurations. Mitigation:
   identity handshakes and translatable classification.
2. **Misuse: decoding without the configuration identity.** IDs collide across configurations (the
   supplier example). Mitigation: a mandatory `schema_id` handshake, the cross-file checks in generated
   code, and strict nested validation.
3. **16-bit limits:** 65,534 domains and 65,534 records per domain. Ample for vehicles, but enforced.
4. **The compiler-side QBS parser rejects extensions:** RC3-era tools can't read Stage B images. Old
   images and the C runtime are unaffected.
5. **Workflow break:** existing build scripts that generate dependencies separately must move to
   root-wide generation.
6. **Whole-configuration `schema_id`:** every change yields a new configuration. Per-record fingerprints
   provide finer compatibility.
7. **Version metadata:** prerelease identity is missing from Git builds until the release-tag field
   exists.

## 15. Open questions

1. Should generation warn when the input looks like a component rather than a configuration root? The
   compiler can't know for certain; a schema-level `configuration: true` marker would be a language
   change.
2. ~~Should the reserved escape values stay reserved?~~ Resolved for A2: domain `0x0000` and locals
   `0x0000`/`0xFFFF` are reserved; domains `0xFF00`–`0xFFFF` are Quarry system domains.
3. Should the record-set compatibility class (§7) be exposed in Stage A's `--describe`, or only in
   Stage B's classifier?
4. Should a future schema-evolution rule (added fields) extend "translatable", or become a fifth class?
5. Should Stage A also add `schema_id` to the generic C runtime's public API, as proposed, or wait for
   Stage B?
