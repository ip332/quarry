# Go Backend

## Implementation Status

`quarry-schema-compiler --language go` generates Go packages for every field
kind the C and Python backends support: `bool`, fixed-width signed/unsigned
integers, `f32`/`f64`, non-negative enums, bounded `string`/`bytes`, bounded
arrays of scalar, enum, string, bytes and record elements, and nested records,
including compiler-resolved cross-namespace enum and record references. The
wire format is BRF v2. Generated code depends only on the Go runtime package
`github.com/ip332/quarry/runtime/go/brf` (`runtime/go/`).

## Purpose

The Go backend lets cloud services and tools exchange BRF records with devices
running the generated C or C++ code, without a separate data definition. It
follows the same principles as the other backends: Schema IR is the only
input, the compiler's canonical BRF v2 layout determines every offset, and
there is no runtime schema interpretation.

## Architecture

`compiler/backend_go` is an independent sibling of the C, C++ and Python
backends. It consumes Schema IR plus the canonical layout computed by
`compiler/layout`, plans one file per namespace that owns records or enums,
and renders it. It does not share code with other backends; its planning
mirrors the Python backend's structure (enum and record catalogs, layout
attachment, output-plan filtering).

### Packages and files

Each namespace segment is a directory; the namespace's file is
`<segments>/<root-file-stem>.quarry.go` (`schema.quarry.go` by default). The
package name is the last segment, lowercased, with non-identifier characters
removed and a trailing `_` for Go keywords (`type.go` becomes package `go_`
in directory `type/go`). The root namespace uses the root file stem as its
package name.

A package that refers to an enum or record of another namespace imports it as
`<--go-import-prefix>/<target segments>` under a generated alias
(`quarrydep0`, ...). The prefix is the Go import path corresponding to the
output directory. It is required only when such a reference exists; without
it, generation fails with a diagnostic naming the field. Dependency roots are
generated by separate compiler invocations into the same output directory, as
for C and Python.

Like the Python backend, the file path depends only on the namespace, so two
`.brd` roots in one namespace map to the same file.

### Names

Records, enums, enum constants and fields become exported identifiers:
words separated by non-alphanumeric characters are capitalized and joined
(`sensor_reading` becomes `SensorReading`; a leading digit gains an `X`).
Enum constants are prefixed with their type (`StatusIdle`), and each record has
a `<Record>RecordID` constant. Struct fields that would collide with a
generated method gain a trailing `_`. Any other post-mapping collision, for
example `foo_bar` and `fooBar`, fails generation as ambiguous rather than
renaming silently.

## Generated API

```go
type Status uint8 // smallest unsigned width holding every declared value

const (
	StatusIdle   Status = 0
	StatusActive Status = 1
)

func (v Status) Valid() bool

const SampleRecordID = 65537 // 0x00010001: domain 1, local record 1

type Sample struct {
	Count    *uint32       // scalar: nil when absent
	Status   *Status       // enum: nil when absent
	Label    string        // absent when empty
	Blob     []byte        // absent when empty
	Readings []float32     // absent when empty
	Child    *other.Child  // nested record: nil when absent
	Children []other.Child // absent when empty
}

func (m *Sample) MarshalBRF() ([]byte, error)
func (m *Sample) AppendBRF(b []byte) ([]byte, error)
func (m *Sample) AppendBRFWithRecordID(b []byte, recordID uint32) ([]byte, error)
func (m *Sample) UnmarshalBRF(data []byte) error
func (m *Sample) UnmarshalBRFWithRecordID(data []byte, recordID uint32) error
```

Pointers give scalars, enums and nested records explicit presence, matching
the C `has_` flags and proto3 `optional`. Strings, bytes and arrays use their
length, as BRF v2 requires: empty values encode as absent, and legacy records
marking them present decode as empty.

Nested records are encoded with the record ID that the *containing* schema
resolves for the referenced record (Schema IR's `record_id` in the containing
compilation), exactly like the C backend's descriptors. The
`...WithRecordID` methods exist for this; `MarshalBRF` and `UnmarshalBRF` use
the record's own ID. Inline fixed-size nested records are written into their
fixed slot; variable-size ones are appended to the variable region.

Encoding validates enum membership, `max_bytes`, UTF-8 for strings and
`max_elements`. Decoding validates the complete record (see
`runtime/go/README.md`) and replaces the destination's contents. Errors are
`*brf.EncodeError` / `*brf.DecodeError` wrapped in `*brf.FieldError` with a
field path such as `children[2].label`. Error precedence follows field order
and is not specified to match the C runtime's; only acceptance is.

## Runtime boundary and compatibility epoch

`runtime/go` is a standalone Go module (`github.com/ip332/quarry/runtime/go`,
Go 1.22 or newer). Its `brf` package provides record writing (`BeginRecord`,
`Put*`, `SetPresent`, `EndVariable`, `FinishRecord`), array framing
(`AppendVaruint`, length prefixes), validation helpers, a `Reader` that checks
headers, presence, absent-slot zeros and the variable region, an `Array`
cursor, and `PeekRecordID` for services that dispatch on record type.

`brf.GeneratedCodeAPIVersion` and the backend's `kGeneratedCodeApiVersionGo`
form the Go generated-code epoch (currently `1`), independent of the other
languages' epochs. Generated files contain two constant conversions that fail
to compile unless the runtime's epoch equals the generator's. The two values
are kept in sync by hand, and `go_codec_interop_test` checks they agree.

## Testing

`tests/interop/go_codec_interop_test.cpp` (skipped when CMake finds no Go
toolchain):

* generated Go for a schema with every field kind and for the benchmark
  schemas (imported nested record, record arrays) is `gofmt`-clean and passes
  `go vet`;
* the runtime's own `go test` suite passes;
* differential test against C: a C harness synthesizes valid records from the
  public C descriptors and mutates them (byte changes, truncation, trailing
  bytes). For 36,000 inputs, Go must accept exactly the inputs C accepts and
  re-encode each to C's canonical bytes. Faults injected into the Go runtime
  (accepting bool 2, skipping absent-slot or unused-bit checks, ignoring
  variable-region contiguity) are detected;
* a Go test of the generated API: presence of zero values, empty-as-absent,
  round trips of every kind, encode validation, containing-schema record IDs
  for nested records, and decode error paths;
* CLI diagnostics: missing `--go-import-prefix`, the prefix without
  `--language go`, ambiguous names, keyword namespaces and `--list-outputs`.

## Known limitations

* One generated file per namespace, as for Python.
* Error offsets are relative to the record or array object being decoded, not
  to the root input.
* Generated encode/decode methods are plain code per field; there is no
  reflection-based or zero-copy decode API.
