# Development Environment

Quarry provides a Docker-based development environment so contributors
can build against the same toolchain CI uses. CI (`.github/workflows/ci.yml`)
builds this repository's `Dockerfile` and runs every configure/build/test step
with `docker compose run`, rather than installing dependencies directly onto
the runner.

## Support policy

| Build | Status |
| --- | --- |
| Docker `debug` | **Authoritative, CI-equivalent.** This is what CI runs. |
| Docker `debug-clang-tidy` | **Authoritative, CI-equivalent.** This is what CI runs. |
| Native `debug` | **Supported, host-dependent.** Works with the dependencies below installed directly; not guaranteed identical to CI's toolchain versions. |
| Native `debug-clang-tidy` | **Best-effort.** Available, but Quarry does not verify or enforce that a native compiler, `protoc`, Protobuf headers, and `clang-tidy` come from a coherent toolchain installation. A native-only clang-tidy include-resolution failure is not treated as a project build defect unless it also reproduces in Docker/CI. |

Native `debug-clang-tidy` failures that don't reproduce in Docker are, by
policy, host toolchain-pairing issues, not Quarry bugs — see
"Troubleshooting a native-only clang-tidy failure" below.

## Build the development image

```sh
docker compose build
```

## Start a development shell

```sh
docker compose run --rm dev bash
```

The repository is bind-mounted at `/workspace` inside the container, so edits
made on the host are visible immediately inside the container, and build
output under `build/` is visible on the host.

## Building and testing inside the container

```sh
cmake --preset debug
cmake --build --preset debug --parallel
ctest --preset debug --output-on-failure
```

## Running clang-tidy inside the container

```sh
cmake --preset debug-clang-tidy
cmake --build --preset debug-clang-tidy --parallel
```

## Toolchain contents

The image (`Dockerfile`) installs:

* Ubuntu 24.04
* `protobuf-compiler`, `libprotobuf-dev`, `libabsl-dev`, `libyaml-dev` via
  `apt-get`
* `clang`, `clang-tidy`, `clang-format` for the `debug-clang-tidy` preset and
  the `.pre-commit-config.yaml` formatting hook
* `pre-commit`, installed with `pipx`

CI builds this image with `docker compose build` and runs every configure,
build, and test step inside it with `docker compose run`. Changing dependency
or toolchain versions for CI means changing the `Dockerfile`, not
`.github/workflows/ci.yml`.

## Native (non-Docker) builds

The presets in `CMakePresets.json` work on any host with the dependencies
above installed directly; see the `Dockerfile` for the authoritative package
list. Native `debug` is supported. Native `debug-clang-tidy` is best-effort
per the support policy above.

## Pre-push validation

Pushed commits are validated locally with the full native `debug` cycle
before they are pushed, and GitHub CI then validates them again
independently. `scripts/quarry-validate` runs the validation; the pre-push
hook only checks its receipts. Running the full cycle inside the hook does
not work: `git push` opens the SSH connection before the hook runs, and GitHub
closes an idle `receive-pack` connection after about six minutes (about 38
minutes with client keepalives), which is shorter than the cycle (issue #89).

### Setup

```sh
pre-commit install                     # pre-commit stage only
scripts/quarry-validate install-hook   # the pre-push hook
```

`install-hook` writes `$(git rev-parse --git-path hooks/pre-push)`, which
honors `core.hooksPath` and is shared by linked worktrees. It replaces a
pre-push hook generated by pre-commit (keeping `pre-push.pre-commit-backup`)
and refuses to replace any other hook without `--force`. The pre-push hook is
not managed by pre-commit because pre-commit passes hooks only the first
outgoing ref. If a pre-commit-generated pre-push hook from before #89 is
still installed, every push fails with instructions to run `install-hook`.

### Workflow

```sh
scripts/quarry-validate push -u origin my-branch   # one step
scripts/quarry-validate validate [<rev>...]        # or validate (default HEAD) ...
git push -u origin my-branch                       # ... then push normally
scripts/quarry-validate status [<rev>...]          # receipt state and reasons
```

`push` runs `git push` with its arguments and hooks enabled. If the hook
reports commits without valid receipts, `push` validates exactly those commits
(the connection is closed by then) and runs the same `git push` once more.
Because Git itself decides what is outgoing, every refspec form works,
including tags, `--all` and `--tags`.

Options for `validate` and `push`:

| Option | Default | Effect |
| --- | --- | --- |
| `--build-jobs N` | `$QUARRY_VALIDATE_BUILD_JOBS`, else CPU count | `cmake --build --parallel N` |
| `--test-jobs N` | `$QUARRY_VALIDATE_TEST_JOBS`, else CPU count | `ctest -j N` |
| `--clean` | off | remove the validation build directory first |
| `--force` | off | revalidate commits that already have a valid receipt |

For `push`, these options must come first; the first other argument starts
the `git push` arguments. Put `--` before `git push` options that share a
name with them, for example `scripts/quarry-validate push -- --force origin
my-branch`.

### What validation runs

For each commit, inside `$(git rev-parse --git-common-dir)/quarry-validation/`:

1. Check out the exact commit, detached, in the reusable linked worktree
   `worktree/`, then `git clean -ffdx` everything except `build/`. The
   developer's working tree, index, untracked files and `build/` are never
   read or modified.
2. Run the commands the pre-push hook used to run, from that worktree's root:
   `cmake --preset debug`, `cmake --build --preset debug --parallel <build-jobs>`
   and `ctest --preset debug -j <test-jobs> --no-tests=error`.
3. Check that the generated `quarry/version.hpp` revision, short SHA and dirty
   flag match the commit's Git-derived version metadata.
4. Record a receipt in `receipts/<commit>/<fingerprint>.json` and a log in
   `logs/<commit>.log`, with step durations.

Every Git, CMake and CTest process gets a sanitized environment: all
repository-selection variables (`git rev-parse --local-env-vars`, the
`GIT_CONFIG*` family, `GIT_EXEC_PATH`) are removed and Git's hook-time
exec-path entry is dropped from `PATH` (#94). Concurrent validations in any
worktree of the clone are serialized by a lock; a second session prints whom
it is waiting for.

### Receipt rules

The hook accepts a pushed ref only if the commit it points to (annotated tags
are peeled) has a receipt with:

- the current validation protocol, the same full commit SHA, and `pass`;
- the same **environment fingerprint** as now: OS and architecture; the
  resolved path and version of `git`, `cmake`, `ctest`, `make`, `cc`, `c++`,
  `python3`, `go`, `protoc` and `pkg-config`; the `pkg-config` versions of
  protobuf, absl and libyaml; the Python `build`, `setuptools` and `protobuf`
  versions; compiler, flag, SDK, pkg-config/CMake path, Go and Python
  environment variables; and every `QUARRY_*` variable except the job counts;
- the same **Git-derived version metadata** as now: what
  `cmake/QuarryVersion.cmake` reads (shallow flag, `git_version` base commit,
  revision count, `git rev-parse --short`, whose length can grow over time).

Deleted refs need no receipt. Every other ref does, including new branches
and tags at commits the remote already has. Amending, rebasing or
cherry-picking creates a new commit that must be validated. Receipts never
expire by time, and parallelism is not part of the fingerprint.

Before a commit is validated, all its existing receipts are removed and a
`running` receipt is written. Only a complete successful run turns it into
`pass`; a failure records `fail` and the failing step, Ctrl-C records
`interrupted`, and a killed run leaves `running`. None of these authorize a
push. When the fingerprint differs from the one the validation build
directory was configured with, its `CMakeCache.txt` and `CMakeFiles/` are
discarded, because CMake reads compilers and flags from the environment only
on a cache's first configure.

### Failures and recovery

| Message from the hook | Meaning | Recovery |
| --- | --- | --- |
| `not validated` | no receipt for this commit (new, amended or rebased) | `scripts/quarry-validate validate <rev>` or `... push ...` |
| `validated in a different environment (...)` | a toolchain, library or variable changed; the first differences are listed | revalidate (incremental) |
| `Git-derived version metadata changed (...)` | for example, a longer `--short` SHA | revalidate |
| `validation failed (<step>; log: ...)` | the commit does not pass | fix, commit, validate |
| `validation is in progress or was killed` / `was interrupted` | no complete run | wait, or revalidate |
| `scripts/quarry-validate is missing from this checkout` | the pushing branch predates #89 | rebase onto a current `main` |

A failed `git push` after the hook passed (for example, a dropped network)
needs no revalidation: push again. If the validation worktree or build
directory gets into a bad state, run with `--clean`, or delete
`.git/quarry-validation/` entirely; the next validation recreates it.

Do not bypass the hook with `git push --no-verify` or a `core.hooksPath`
override unless a maintainer has explicitly authorized that specific push.

### Limitations

- Only the tip commit of each pushed ref is validated, not every intermediate
  commit; CI validates pushed and pull-request heads the same way.
- The fingerprint cannot see everything: a system library upgraded without a
  version change, network-dependent behavior, or flaky tests. GitHub CI
  remains the authoritative validation.
- The validation build directory needs about as much disk space as
  `build/debug` (around 500 MB).
- macOS and Linux only (`fcntl` locking); Git 2.31 or newer and Python 3.8 or
  newer.

## Troubleshooting a native-only clang-tidy failure

1. Reproduce inside Docker first:

   ```sh
   docker compose build
   docker compose run --rm dev cmake --preset debug-clang-tidy
   docker compose run --rm dev cmake --build --preset debug-clang-tidy --parallel
   ```

2. If Docker passes, the failure is specific to your host — inspect your host
   toolchain pairing rather than the CMake build.
3. Verify the paths and versions of the configured C++ compiler, `clang-tidy`,
   `protoc`, and the Protobuf headers your compiler resolves at build time.
   A mismatch between where your compiler's implicit include search finds
   Protobuf headers and where your `clang-tidy` binary's implicit search
   looks is the most common cause (see background below).
4. Do not modify Quarry CMake files merely to mask a host-only implicit
   include-path mismatch — add an explicit include path, disable a warning,
   or exclude a generated source. If Docker/CI is unaffected, the fix belongs
   in your host environment, not the repository.

## Generated-code lint policy

Generated Protobuf sources (`schema_ir.pb.cc`/`schema_ir.pb.h`) are linted by
clang-tidy the same as handwritten sources; `compiler/CMakeLists.txt` does not
set `SKIP_LINTING` on them. (Only `yaml/yaml_parser.cpp`, a libyaml C-API
wrapper, carries `SKIP_LINTING`, for unrelated reasons.) In the authoritative
Docker/CI environment, `debug-clang-tidy` lints generated Protobuf code
cleanly — stylistic warnings only, no errors, since `.clang-tidy`'s
`WarningsAsErrors` is empty.

## Background: why native clang-tidy can diverge from Docker/CI

A `google/protobuf/runtime_version.h` file-not-found error compiling generated
`schema_ir.pb.cc` under `debug-clang-tidy` was previously seen on one native
macOS setup and mistaken for a project infrastructure blocker. It does not
reproduce in Docker or CI. Two conditions, confirmed by comparing the
reference environment (Ubuntu 24.04, apt Protobuf 3.21.12, apt
`clang-tidy-18`) against the failing native setup (Homebrew Protobuf 35.1,
Apple Clang as the configured compiler, a separately installed Homebrew LLVM
`clang-tidy`), both have to hold:

1. **A Protobuf generator new enough to emit the guard.** `runtime_version.h`
   is generated only by newer `protoc` versions. Ubuntu's apt Protobuf
   (matching Docker/CI) doesn't emit it, so the failure mode cannot occur
   there regardless of toolchain pairing.
2. **A compiler and clang-tidy binary with different implicit include search
   paths.** CMake omits an explicit `-isystem` flag for `Protobuf_INCLUDE_DIRS`
   when it's already implicit for the *configured compiler* — correct, and
   harmless when the same binary (or a coherently paired one) also runs
   clang-tidy. It becomes a problem only when `CMAKE_CXX_CLANG_TIDY` invokes a
   separately installed `clang-tidy` binary whose own implicit search path
   doesn't include the directory the configured compiler resolved implicitly
   (e.g. a Homebrew LLVM `clang-tidy` next to Apple Clang as the compiler).
   Docker/CI use one coherent apt-installed toolchain for both roles, so this
   divergence cannot occur there.

Both conditions are host toolchain-installation choices, not project build
configuration. No CMake, `.clang-tidy`, or generated-code change fixes them
without either overfitting one host's layout or masking the actual
divergence — so none was made. `.github/workflows/ci.yml`'s `clang-tidy` job
runs `debug-clang-tidy` in Docker on every push/PR as the durable regression
check for the authoritative environment.

## Coverage

The canonical coverage environment is Docker. It uses GCC/gcovr for native
compiler and backend coverage, and Python `coverage.py` for the pure-Python
runtime:

```sh
docker compose build
docker compose run --rm dev cmake --preset coverage
docker compose run --rm dev cmake --build --preset coverage --parallel
docker compose run --rm dev ctest --preset coverage \
  -E "backend_codegen_test|runtime_package_consumer_test|schema_compiler_install_test|schema_compiler_package_test|public_examples_test" \
  --output-on-failure
docker compose run --rm dev sh -c \
  'mkdir -p coverage && gcovr --root . --object-directory build/coverage \
   --filter "^(compiler|include)/.*" \
   --exclude ".*tests.*" --exclude ".*generated.*" --exclude ".*_deps.*" \
   --json-summary-pretty --json-summary coverage/native.json \
   --html-details coverage/native.html --txt coverage/native.txt'
docker compose run --rm dev sh -c \
  'PYTHONPATH=runtime/python/src python3 -m coverage run --branch --source=runtime/python/src \
   -m unittest discover -s runtime/python/tests && \
   python3 -m coverage json -o coverage/python.json'
docker compose run --rm dev python3 tools/coverage_guard.py \
  --native coverage/native.json --python coverage/python.json \
  --baseline tools/coverage_baseline.json
```

The coverage run omits only the slowest integration tests that compile many
temporary downstream/generated programs; those remain required in the normal
full CTest CI job. The checked-in baseline measures native
line/function/branch coverage and
Python line/branch coverage separately. The guard allows a one percentage
point decrease in any measured metric to avoid unstable rounding failures;
an intentional decrease must update the baseline in the same reviewed change
and include the reason. Tests, generated sources, third-party code, build
trees, temporary consumer trees, and system headers are excluded. Detailed
HTML and text reports are produced as CI artifacts.
